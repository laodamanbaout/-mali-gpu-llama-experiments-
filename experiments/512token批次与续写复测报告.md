# 512 token 输入的 GPU 批次和续写复测

设备 Redmi K50 / 天玑 8100 / Mali-G610，Android 14，ARM r32p1；Qwen2.5-7B-Instruct IQ1_S；实验性 llama.cpp 隔离构建。使用 `long-context/synthetic-512.txt` 的前 512 个 token，模型上下文 1024、逻辑批次 512、4 线程、关闭 Flash Attention。GPU 模式强制词嵌入和输出权重进入 Vulkan0，启用大 Q5、选择性 FP32、FP16 ROPE 融合绕行三个实验选项。

## 前缀处理

| 模式 | 物理批次 | 处理时间（秒） | 速度（token/秒） | 次数 |
|---|---:|---:|---:|---:|
| CPU | 32 | 104.879 | 4.882 | 1 |
| CPU | 64 | 104.878 | 4.882 | 1 |
| 全 GPU 模型计算 | 32 | 266.556 | 1.921 | 1 |
| 全 GPU 模型计算 | 64 | 173.041、172.404 | 2.959、2.970 | 2 |

计时为探针内 `llama_process` 和同步，不包含模型加载。GPU 批次 64 相对于批次 32 该次结果约提升 54%–55%，但批次 32 只有一次、执行时间不在同一时刻；没有固定设备频率或后台任务，且输入只有一条。不能保证所有输入、设备、上下文或生成速度有同等提升。

GPU 三次的完整词表 152064 个分数逐位相同。CPU 两次完整词表分数也相同；CPU/GPU 的前五候选顺序一致，但 softmax 总变差约 0.09266，且 CPU 本身有量化近似误差，因此这个对照不能当作完整正确性证明。

批次 64 的 Vulkan 计算缓冲约 41.13 MiB，批次 32 约 20.56 MiB；这不是整个进程或独立显存总量。批次 64 首次运行中一次系统 `MemAvailable` 采样约 1.11 GiB，前后约 3.34、3.33 GiB；系统保护没有关闭，采样不能证明其他后台进程没有受到影响。

## 连续生成

同一 512 token 前缀后，CPU 一次和 GPU 批次 64 两次均按贪心选择生成 8 个 token，三次的 token ID 相同：

```text
448, 264, 1682, 13, 362, 2805, 6010, 389
```

对应文本为 ` with a child. A short distance on`。第一个 token 来自前缀的最后一组分数，其余七个逐个输入并更新 KV 缓存。GPU 两次日志记录前缀和单 token 推理为 Vulkan0 分段；采样、分词和调度依然由 CPU 完成。只有一个合成输入和短续写，不能证明更长输出一致或者模型回答正确。

## 文件

- `batch512/batch512-probe.cpp`：相对上次探针，只增加了 512 token 测试选择物理批次 64 的能力；不修改 llama.cpp 源码。
- `batch512/gpu-512-ub64.log`、`gpu-512-ub64-repeat.log`、`cpu-512-ub64-gen8.log`：本次原始日志，前缀 logits 为同名 `.bin`。
- `batch512/comparison.txt` 和 `compare.py`：词表分数对照；旧的批次 32 对照文件在 `long-context/`。
- `batch512/run-batch512.py`：本机运行脚本，包含本机路径；已有日志时会拒绝覆盖。分享前应审查用户名和路径。

首次 GPU 512 token 测试产生的批次 32 原始日志及 CPU 数据见《长输入和批次实验报告》。此前 IQ3_S 全 GPU 曾触发系统内存保护，本试验不能说明其已适用。
