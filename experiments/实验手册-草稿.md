# Redmi K50 Mali Vulkan 兼容性实验手册（草稿）

本手册记录一次不 Root、不解锁、不刷机的实验。它适用于复查和继续研究，不是通用安装教程或已经验证可上游合并的修复。

## 为什么要做

手机的 Mali GPU 能被 llama.cpp 的 Vulkan 后端识别，但原程序在向 Vulkan 队列提交工作时崩溃。能够枚举设备不代表已经成功提交 GPU 工作，也不代表模型计算正确。

## 已确认的现象

在 Redmi K50、Android 14、Mali-G610 MC6、ARM r32p1、物理设备 Vulkan 1.1.177 上，独立程序创建标志为零的普通队列后：`vkGetDeviceQueue2` 返回空句柄；`vkGetDeviceQueue` 返回非空句柄，空提交和带 fence 的空命令缓冲区提交成功。实验版 llama.cpp 中两个队列也出现相同的空句柄现象。

实验版仅在普通队列创建标志为零且 `getQueue2` 失败时尝试 `getQueue`，避免向提交函数传空句柄。Vulkan 规范规定，`vkGetDeviceQueue` 只能用于创建标志为零的队列；不能直接用于有非零标志的队列。

这是一种应用层兼容性实验，不能据此判断缺陷位于 Android loader 还是 ARM 驱动，也不能推断所有 Mali 设备都相同。实验代码包含日志和 abort，尚不是生产补丁。

## 如何复现基础队列测试

需要手机上已经安装可用的 Termux、clang、Vulkan headers 和链接库。先保存原有环境，不覆盖系统或 Termux 已有 Vulkan 库。本目录的 `queue-probe.c` 是独立程序：

```sh
clang -O0 -g -Wall -Wextra queue-probe.c -o queue_probe -lvulkan
./queue_probe
```

检查 `queue legacy=... queue2=...` 和两次 `vkQueueSubmit`、`vkWaitForFences` 的结果。输出 `PASS` 表示其中的普通队列、空提交和 fence 测试成功，并不意味着神经网络计算经过验证。

## llama.cpp 实验版

目前实验副本在本机 Termux 的 `~/mali-diagnostics-20261101/llama-copy`，原始源码目录不受影响。构建版本来自原手机源码快照，源码原目录没有 Git 提交历史，无法确认精确上游 commit，因此暂不能把本实验差异当成可直接套用到任意上游版本的补丁。`queue-diagnostic.patch` 是此次实验记录。

示例运行方式（模型路径按实际情况填写）：

```sh
export PREFIX=/data/data/com.termux/files/usr
export PATH="$PREFIX/bin:$PATH"
export EXP="$HOME/mali-diagnostics-20261101/llama-copy"
export LD_LIBRARY_PATH="$EXP/build/bin"
"$EXP/build/bin/llama-completion" \
  -m "$HOME/models/Qwen2.5-7B-Instruct.i1-IQ1_S.gguf" \
  -c 128 -n 32 -ngl 99 -t 4 -b 32 -ub 32 \
  --temp 0 -no-cnv --no-warmup -fit off \
  -p "The capital of France is"
```

实验日志曾记录 29/29 层卸载以及 Vulkan 模型缓冲区，32 token 生成完成约 1.18 token/s。数字只代表当次短测试，包含硬件、模型、参数与状态的影响。CPU 对照约 3.51 token/s，条件和样本有限。GPU 能运行不代表一定更快。

## 正确性检查

已完成：IQ1_S 矩阵乘法 49/49、F16 矩阵乘法 373/373，以及 RMS_NORM、SOFT_MAX、ROPE、GET_ROWS 合计 983/983 测试通过。测试覆盖有限。

同一前缀的全词表分数显示 CPU 和 GPU 的首选词会不同；关闭 Flash Attention 后，CPU 与 GPU 的首选词一致，但分布仍不同。CPU 自身开启与关闭 Flash Attention 时也发生变化。因此不能简单声称已定位计算错误或完全正确。需要更多模型、长度、逐层数值和注意力路径对照。

## 补充对照结果

受限 F16 Flash Attention 测试通过 338/338；较宽范围测试因包含超大输入而主动停止，不能标为全套通过。IQ3_S 在同一短前缀下 CPU/GPU 的前五个候选词顺序一致，概率分布总变差距离约 0.0114；相同短提示的 16 token 生成文本一致。IQ1_S 的对应分数差异较大，CPU 自身开启和关闭 Flash Attention 时首选词也会变化。上述均不是完整模型精度保证。

IQ3_S 单次短测试的 CPU/GPU 生成速度分别约 1.56/0.92 token/s。尚不能确定 GPU 较慢的原因；后续需要固定热状态、重复次数、prompt 长度并分析各阶段。

## 新增：注意力重复性实验

在当前 K50 上，独立注意力测试固定输入并重复 20 次：默认 GPU 路径在 batch 4–64 出现微小数值变化；实验性 row_split=1 调度在 1、4、8、11、16、32、64 七组中未出现变化。两份模型各两次相同前缀 logits 也一致；338/338 个选定 Flash Attention 回归用例通过。覆盖有限，不应称为通用修复。

可选择继续使用关闭 Flash Attention 的隔离启动脚本；另有只对 ARM 并显式启用实验开关的 Flash Attention 启动脚本。具体路径、基准和限制见 `Mali深入排查报告.md`。原始源码和模型不受影响。

## 补充：长提示词与性能

使用实验版的 128 token 合成提示，IQ3_S 的 GPU 两次为 3.85/3.84 token/s，CPU 两次为 2.27/2.26；与此前短生成中 CPU 更快的结果不同。IQ1_S 单次为 CPU 5.08、GPU 4.00 token/s。不能笼统地说 GPU 在所有工作负载都更慢。

实验性修正性能计时查询后，计时显示量化矩阵乘法占据此短测试的主要 GPU 时间；该模式会引入额外同步，仍需常规基准验证。修改矩阵运算调度的两项初筛均未提速，现已恢复此前实验版本。详细数值和限制见《Mali深入排查报告》。

IQ3_S 的 128 token 合成提示补测中，GPU 关闭 Flash Attention 两次为 3.81/3.82 token/s，实验开关开启 Flash Attention 两次为 3.85/3.84；两者接近。这只覆盖一种输入长度和设备。

后续补充：两份模型均完成 CPU 与 GPU 的 64 token 生成；IQ3_S 的两个 GPU 注意力配置在该次测试中输出一致，但与 CPU 后续文本不同。固定 512 token 重复短句前缀下，IQ3_S 的 CPU、GPU 关闭 Flash Attention 和 GPU 实验分组均完成并选中同一个首选词。该输入高度可预测，不能代替真实数据集正确性验证。详细速度、数值和局限见《Mali深入排查报告》。

采用非重复 128 token 英文输入补充 IQ3_S 分数比较，CPU 与两种 GPU 配置前三候选词一致，但分布仍有差异；这是一条样本，不能代表全面正确性。详细数据见深入排查报告。
